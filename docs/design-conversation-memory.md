# 設計草案：對話記憶與上下文判讀

狀態：階段 0（只記錄）已實作；階段 1 之後尚未實作。範圍已跟使用者確認：記憶保存 2～3 天、做成開關、先只用在「接續上一件事」。

## 1. 要解決什麼

使用者的句子常常接著上一句，現在每則訊息都是獨立的：

| 使用者說 | 現在發生什麼 | 想要的行為 |
|---|---|---|
| 「看牙醫改到明天」→（確認卡）→「改下午三點」 | 後一句被當成新待辦 | 知道是在改剛剛那件事 |
| 「明天下午開會」→「地點在 A 教室」 | 變成一則沒關聯的筆記 | 補到那件事上（第二階段） |
| 「剛剛那個取消」 | 沒有「剛剛」可指 | 找到剛剛那件，給確認卡 |

## 2. 不做什麼

- 不改成讓模型自己選工具的 agent（維持 Rule 5：模型只負責「判斷這句話在指什麼」，路由和寫入仍是寫死的程式）。
- 不增加 Gemini 呼叫次數：一則訊息仍然最多打一次分類。
- 不改本地快速分類（`localclassify`）：那條路不經過 AI，也就不吃上下文。

## 3. 資料

新增一張短期表，不放進 `notes`，因為它不是使用者的記錄：

```sql
create table if not exists public.conversation_turns (
  id uuid primary key default gen_random_uuid(),
  role text not null check (role in ('user', 'bot')),
  text text not null,                      -- 截到 200 字；bot 的 Flex 卡片只存 altText
  kind text,                               -- 當時的分類：task / note / query / action ...
  ref_note_id uuid references public.notes(id) on delete set null,  -- 這一輪碰到哪一筆事項
  created_at timestamptz not null default now(),
  expires_at timestamptz not null default (now() + interval '3 days')
);
create index if not exists idx_turns_recent on public.conversation_turns (created_at desc);
```

重點是 `ref_note_id`：記下「這一輪講的是哪一筆事項」，之後的接話可以直接指到那一筆，
不用再靠關鍵字去模糊比對（現在的 `target` 比對在同名事項多筆時會選錯）。

保存：3 天。讀取時只讀 `expires_at > now()`；過期資料由每天一次的清理刪掉
（沿用語音檔清理的做法：每天只跑一次的狀態旗標）。另加一個指令「清除記憶」，一鍵刪光。

## 4. 寫入時機

- 在 webhook 處理文字／語音訊息時：先記使用者的字，回覆送出後記 bot 的一行摘要。
- 摘要：字串回覆取前 200 字；Flex 取 `altText`；不存卡片 JSON。
- `ref_note_id`：處理函式知道自己動了哪一筆（新增時有 `data.id`、改動時有找到的那筆），
  透過一個每次請求自己的小物件回報，不用全域變數（避免並行請求互相覆蓋）。
- 寫入失敗只記 log，不影響回覆。
- 開關關閉時完全不寫入。

## 5. 什麼時候帶上下文（閘門）

全部成立才帶，否則維持現在的行為：

1. 開關是開的。
2. 這句話走到 AI 分類（本地快速分類成功的不帶）。
3. 最近一輪 bot 回覆有 `ref_note_id`（上一件事確實動到某筆事項）。
4. 句子短（約 20 字內）或含指代／接續詞：那個、剛剛、剛才、它、這個、再、也、還有、順便、改成、同樣。

帶的內容：最近最多 6 輪，每輪附相對時間（例如「5 分鐘前」「昨天」），
合計約 800 字以內。額外的 token 很少，也不增加呼叫次數。

## 6. 分類器的變化

提示詞多一段「最近對話」，輸出多一個欄位：

```json
{ "ref_turn": "最近對話裡第幾輪（從最新往回數 1、2…），沒有指代就 null" }
```

程式把 `ref_turn` 對回該輪的 `ref_note_id`：

- 分類為 `action`（改時間、改內容、完成、取消）且有 `ref_note_id` →
  直接用那一筆，跳過關鍵字比對；找不到或已完成再退回現有流程。
- 其他分類：忽略 `ref_turn`，行為跟現在一樣。

這就是「先只對修改既有事項啟用」：上下文只會影響 `action` 這一條路。

## 7. 安全

- 破壞性動作（取消、刪除、完成）一律先給確認卡，卡片上寫出是哪一筆
  （例如「要改的是：看牙醫 10/31 15:00 嗎？」），猜錯的話一眼就看得出來。
- 既有的「撤銷」按鈕保留。
- 模型回傳的 `ref_turn` 必須是整數且在範圍內，否則當作沒有；對回的筆記必須仍存在、未刪除。
- 隱私：只存短期、只存截斷後的文字、可一鍵清除；不存圖片辨識內容與檔案。

## 8. 開關

沿用現有功能開關機制（`lib/modules.js`），新增一個「對話記憶」模組，預設關閉。
後台新增開關時要依 Rule 15 補上教學步驟（`data-tour`），並依 Rule 16 更新 CHANGELOG。

## 9. 測試

1. 純函式：閘門判斷（指代詞、長度、是否有 `ref_note_id`、過期輪次）。
2. 提示詞組裝：輪次排序、相對時間、字數上限。
3. `ref_turn` 驗證：非整數、越界、筆記已不存在。
4. 對話劇本（Gemini 以替身模擬）：約 15 組，涵蓋「改到明天→改下午三點」「剛剛那個取消」
   「新事情但剛好很短」（不該誤接）等，確認不誤接、誤接時有確認卡擋住。
5. 開關關閉時的行為與現在完全相同（既有 344 項測試必須全過）。
6. 上線前的實機檢查表：在 LINE 上實際走一遍上面的劇本。

## 10. 分階段

| 階段 | 內容 | 風險 |
|---|---|---|
| 0 | 資料表、寫入、清理、「清除記憶」；不影響判斷 | 低 |
| 1 | 閘門 + 提示詞 + `ref_turn` 只用在 `action` | 中（誤接，但有確認卡） |
| 2 | 新增 `append` 動作（補充到既有事項）、查詢類接話（「那後天呢？」） | 中 |
| 3 | 視使用狀況，再評估要不要讓模型多步驟呼叫工具 | 另案 |

## 11. 已知限制

- 誤接：很短的新事情可能被當成接話。閘門條件和確認卡是為了降低影響，第一版要靠實際使用調整詞表。
- 「接話」只在有 `ref_note_id` 時成立；純聊天式的上下文（沒動到任何事項）第一版不處理。
- 記憶只有 3 天，超過就當全新對話（符合使用習慣：很少超過 5 天才回頭交辦）。
- 我沒有實測 flash-lite 對中文省略句的判讀正確率，階段 1 之前要先用對話劇本量一次。

## 12. 需要使用者決定

2. 「清除記憶」要做成 LINE 指令、後台按鈕，還是兩者都要？
